Estado del proyecto FitNova

Informe de situación · 11 de noviembre de 2026 · Repositorio alinaresblanco-gif/FitNova (rama main)

1 · Visión general

El proyecto está formado por dos aplicaciones web conectadas por un backend común en Supabase. Ambas apps son HTML/CSS/JS estático (sin framework) y comparten el mismo proyecto de base de datos mediante la clave publicable, protegida por políticas RLS.

PiezaQué esCarpeta
FitNova Manager App del entrenador / profesional (escritorio): gestión de clientes, agenda, equipo, librería, negocio fitnova-manager/
FitNova Go App del cliente final (PWA móvil instalable): onboarding, perfil, métricas, vídeos, agenda mockup-fitnova-go/
Backend Supabase Postgres + autenticación + funciones RPC. Proyecto fitnova-dev, ya enlazado con la CLI supabase/

2 · Lo que YA está hecho y funciona

COMPLETADO

Backend: esquema de datos v1 + seguridad

Hay 4 migraciones SQL en supabase/migrations/:

  • clientes_core.sql — Todo el esquema v1: tablas profesionales, clientes, invitaciones, profesional_cliente, clientes_objetivo, clientes_salud_parq (cuestionario PAR-Q), clientes_metricas, consentimientos, etiquetas y cliente_etiqueta. RLS activado en las 10 tablas: el cliente solo ve lo suyo; el profesional solo ve sus clientes asignados; los datos de salud solo los ven entrenador y nutricionista.
  • clientes_rpc.sql — Las 5 funciones que conectan las dos apps:
    • registrar_profesional_actual — autorregistro del profesional tras crear cuenta
    • profesional_actual_id — helper de identidad
    • crear_invitacion — crea el cliente en estado invitación enviada + token único (SHA-256, caducidad 7 días, solo una invitación vigente por cliente)
    • obtener_invitacion — Go valida el token sin necesidad de sesión
    • completar_onboarding — transacción atómica: guarda perfil + objetivo + PAR-Q + peso inicial + consentimientos, vincula la cuenta y activa al cliente
  • Dos fixes de crear_invitacion (ambigüedad de nombres de columna). La versión final devuelve (invitacion_id, token, expira_en).
COMPLETADO

El flujo Manager ↔ Go (la relación entre las apps)

Es el corazón del trabajo y ya funciona de punta a punta:

  1. Manager — el profesional crea cuenta / inicia sesión (login.html con Supabase Auth real) y completa su perfil profesional.
  2. Manager → clientes.js — el botón «Añadir cliente» llama a crear_invitacion y genera el enlace con token hacia invitacion.html de Go (hoy se copia manualmente; aún no se envía email).
  3. Go → invitacion.js — valida el token y muestra el onboarding completo: crear cuenta con contraseña, género, objetivo, fecha de nacimiento, peso, altura y las 7 preguntas PAR-Q. Al finalizar llama a completar_onboarding.
  4. Resultado — el cliente pasa automáticamente de la pestaña «Invitaciones» a «Activos» en Manager.
  5. Manager — la lista de clientes activos, las invitaciones pendientes y la ficha de cliente (cliente-perfil.js) cargan datos reales de la base de datos.

Además, todas las páginas de Manager tienen guarda de sesión (redirigen a login si no hay sesión) y botón de cerrar sesión en el avatar.

3 · Lo que sigue siendo maqueta (sin datos reales)

MAQUETA

FitNova Manager

  • Dashboard, Agenda, Chat, Equipo, Librería y Negocio — maquetados con buen diseño pero con datos ficticios en el HTML. Solo hay JS genérico de interfaz (modales, pestañas) en app.js.
  • En la ficha de cliente, solo el Resumen carga datos reales; el resto de pestañas (entrenamientos, nutrición, progreso, documentos…) son estáticas.
MAQUETA

FitNova Go

  • Es una PWA ya montada: manifest, service worker y sistema de aviso de actualización de versión.
  • Inicio, Agenda, Perfil, Vídeos y Ajustes funcionan en modo simulación: su app.js guarda actividades y métricas en localStorage, no en Supabase.
  • Lo único conectado a backend real es invitacion.html (el onboarding).
  • Tras el onboarding, el cliente aterriza en index.html pero no hay login de cliente ni carga de sus datos reales: la sesión creada durante el onboarding no se aprovecha en el resto de la app.
